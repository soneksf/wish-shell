# wish — простий Unix-шелл

Лабораторна робота з курсу «Операційні системи з розподілом часу».
Реалізація завдання [OSTEP `processes-shell`](https://github.com/remzi-arpacidusseau/ostep-projects/blob/master/processes-shell/README.md)
мовою C++17 з використанням POSIX API.

**Статус: усі 22 офіційні тести проходять.**

---

## Про що робота

Шелл — це програма-посередник між користувачем і ядром операційної системи.
Коли в терміналі набрано `ls -la`, ядро цього тексту не бачить: текст читає шелл,
розбирає його на частини, знаходить на диску файл `/bin/ls`, просить ядро створити
новий процес, запускає в ньому знайдену програму, дочікується її завершення і знову
показує запрошення.

Ключова особливість: шелл **не вміє** виконувати `ls`, `cat` чи `echo`. У ньому немає
їхнього коду. Крім трьох вбудованих команд, уся його робота — знайти потрібний файл
і попросити ядро запустити його в окремому процесі.

Мета роботи — на практиці пройти процесний API, тобто той набір системних викликів,
через який операційна система дає програмам доступ до процесора: `fork()`, `execv()`,
`waitpid()`. Попутно зачіпаються файлові дескриптори, робочий каталог процесу,
перенаправлення стандартних потоків і коди завершення.

## Що реалізовано

- інтерактивний режим із запрошенням `wish> ` та пакетний режим (команди читаються з файлу)
- запуск зовнішніх програм у дочірніх процесах через `fork()` + `execv()`
- власний шлях пошуку виконуваних файлів із перевіркою через `access()`
- вбудовані команди `exit`, `cd`, `path`
- перенаправлення виводу у файл через `>` — причому у файл потрапляє і `stdout`, і `stderr`
- паралельний запуск кількох команд одного рядка через `&`
- обробка синтаксичних помилок із єдиним повідомленням `An error has occurred`
- завершення з кодом `1` при фатальних помилках запуску, `0` — при `exit` та EOF

## Етапи розроблення

Робота велася поетапно, кожен етап — окремий коміт і робоча програма, яка вміє трохи
більше за попередню. Знімки коду кожного етапу збережені в теці `stages/`.

| Етап | Що додано | Системні виклики |
|:---:|---|---|
| 1 | Цикл читання рядків, запрошення `wish> `, вихід по `exit` та EOF | `getline` |
| 2 | Запуск зовнішніх програм у дочірньому процесі | `fork`, `execv`, `waitpid` |
| 3 | Шлях пошуку виконуваних файлів, вбудована команда `path` | `access` |
| 4 | Вбудовані `cd` та `exit` з перевіркою кількості аргументів | `chdir` |
| 5 | Перенаправлення виводу у файл | `open`, `dup2`, `close` |
| 6 | Паралельне виконання команд одного рядка | кілька `fork` до першого `waitpid` |
| 7 | Пакетний режим та коди завершення | `fopen`, `exit` |

Переглянути різницю між сусідніми етапами:

```bash
diff -u stages/04/src/shell.cpp stages/05/src/shell.cpp
```

## Структура

| Файл | Відповідальність |
|---|---|
| `src/main.cpp` | Вибір режиму роботи та цикл читання команд |
| `src/parser.h/.cpp` | Розбиття рядка на лексеми, розділення по `&`, розбір і валідація `>` |
| `src/shell.h/.cpp` | Шлях пошуку, вбудовані команди, створення процесів, перенаправлення |
| `src/error.h/.cpp` | Єдине повідомлення про помилку у `stderr` |

Розділення зроблено так, щоб кожен файл відповідав за одну річ: `parser` перетворює
текст на структуровані дані й позначає синтаксичні помилки прапорцем, але нічого не
виводить; рішення, що робити з помилкою, приймає `shell`.

## Збірка та запуск

Потрібен Linux (проєкт розроблявся в Ubuntu 24.04 під WSL2) і `g++` з підтримкою C++17.
Під Windows проєкт не збирається принципово — `fork()` там не існує.

```bash
make            # збирає виконуваний файл ./wish
./wish          # інтерактивний режим
./wish batch.txt  # пакетний режим: команди читаються з файлу, запрошення не друкується
make clean
```

Приклад роботи:

```
wish> ls -la /tmp
wish> path /bin /usr/bin
wish> cd /usr/share
wish> ls > output.txt
wish> sleep 3 & sleep 1 & echo старт
wish> exit
```

## Тестування

Використано офіційний набір тестів OSTEP (теки `tests/` і `tester/`):

```bash
make && ./test-wish.sh
./test-wish.sh -c      # при падінні показує різницю очікуваного й отриманого
./test-wish.sh -t 14   # лише один тест
```

Тести перевіряють не тільки базову функціональність, а й крайні випадки: порожній
шлях пошуку, відсутність команди перед `>`, кілька файлів після нього, аргументи
в `exit`, коди завершення при поганому пакетному файлі.

## Ключові рішення

**Чому `fork` перед `execv`.** `execv` не запускає програму поруч — він замінює вміст
поточного процесу новою програмою. Без `fork` шелл замінив би сам себе: команда
виконалася б один раз, і процес шелла перестав би існувати. `fork` створює копію,
якою можна пожертвувати.

**Спершу всі процеси, потім очікування.** У `run_line` два окремі цикли: перший робить
`fork` для всіх команд рядка і збирає їхні PID, другий викликає `waitpid` для кожного.
Якби очікування стояло всередині першого циклу, команди виконувалися б послідовно і
ніякої паралельності `&` не давав би.

**Пошук програми — до `fork`.** `resolve()` викликається в батьківському процесі. Якби
пошук робився в нащадку, то для `неіснуюча > out.txt` перенаправлення вже спрацювало б,
і повідомлення про помилку потрапило б у файл замість екрана.

**`dup2` — у нащадку.** Перенаправлення стосується однієї команди, а не шелла. Виклик
у батьківському процесі перенаправив би сам шелл разом із запрошенням, причому
безповоротно — оригінальний дескриптор `1` було б затерто.

**Вбудовані команди виконуються в процесі шелла.** `exit`, `cd` і `path` мусять бути
вбудованими, бо їхній ефект має пережити команду: `chdir` у дочірньому процесі змінив би
каталог нащадка, який одразу завершується, а новий шлях пошуку помер би разом із ним —
процеси мають ізольовану пам'ять.

**`_exit` замість `exit` у нащадку.** Звичайний `exit` скидає буфери stdio, а нащадок
успадкував копію батьківських буферів і надрукував би їхній вміст удруге.
